履歴を捨てると逆に高くつく — Stateful Agent 対照実験

会話履歴の代わりに構造化 state を持つ設計が、実運用で軽くなるかを対照実験で検証した。結論は否定的である。履歴を持つ full が最も安く、履歴を捨てた2モードは33%高い。キャッシュの作り直しが原因である。

対象: devtch リポジトリ3モード比較（各5ターン時点）claude.ai サブスク枠

エグゼクティブサマリー

  1. 履歴を持つ full が最も安い。同一5ターンで $0.67/ターン。履歴を捨てた stateless（$1.00）・recent（$0.99）より33%安く、設計の狙いと逆の結果になった。
  2. 原因はキャッシュの作り直し。毎ターン新しいセッションを作る2モードは cache_creation が入力の12%前後に達する。継続する full は5.2%で済む。書き込みは読み込みより単価が高い。
  3. state は12ターンで10.8倍に膨張した。3,691B → 39,732B の線形増加。履歴を捨てても、同じものが state という別の形で積み上がる。
  4. 次の一手は2つ。state の刈り込み（アーカイブ方式）と、セッション継続の見直し。後者は設計の根幹に関わる。

01実験の設計

同じプロンプト列を、履歴の持ち方だけ変えて流す対照実験とした。

単発の質問を各モードで1回ずつ投げても差は出ない。履歴を捨てる効果はターンが積み上がって初めて現れるため、会話が継続する7問のシナリオを巡回させる方式を採った。

02state の膨張

stateless モードでも state は線形に増え続け、12ターンで10.8倍になった。

原因は明確である。決定レコードは 追記される一方で、消える仕組みがない。部分更新（決定+）を導入して既存の書き直しは止めたが、蓄積そのものは止まらない。

規約には「確定して動かないものは統合してよい」と書いてあるが、モデルは統合しない。追記のほうが出力として楽だからである。指示だけでは制御できない。

recent モードでも同じ傾向

進行中の recent モード（4ターン時点）でも +2,858B/ターンと、ほぼ同じ傾きを示している。モードによらず state は膨らむということである。

差を生んでいるのはキャッシュ作成（cache_creation）である。キャッシュへの書き込みは読み込みより単価が高く、通常5倍程度になる。

stateless と recent は毎ターン新しいセッションを作るため、キャッシュを作り直し続ける。入力に対する比率は12%前後に達する。一方 full は resume でセッションを継続するので5.2%で済む。

入力トークン（in）は指標として使えない。full は履歴がキャッシュに乗るため in=1 まで落ちることがある。in が小さいことは、プロンプトが小さいことを意味しない。

履歴を一切持たない stateless と、直近3ターンを持つ recent の間に有意な差はない。state の増加速度に至っては stateless の方がわずかに少ない程度で、実質同じである。

入力トークンが十数まで落ちている一方、キャッシュ読み込みは35〜45万トークン規模である。この差が示すのは、コストの出所が履歴ではなくエージェントの作業そのものだということである。ファイルを読んで評価する仕事をしている以上、この量は削れない。

state が効いた瞬間もあった

recent の最終ターンだけ cache_read が 58,802 と、他（16万〜61万）の10分の1に落ちた。同じシナリオの同じ位置なので、モデルがファイルを読まず state だけで答えたと見られる。ただし24ターン中1回であり、再現性は確認できていない。

金額表示（costUSD）は SDK が list price で計算した参考値であり、実際の請求額ではない。実際に消費しているのは claude.ai サブスクのレート枠（5時間枠・7日枠）である。

05設計の前提が崩れている点

論文の定式は state が有界である前提だが、実装には上限も刈り込みもない。

SKILL.state の Σt+1 = Σt ⊕ ΔΣt は、state が一定規模に収まることを暗黙の前提としている。実測はこの前提が成立していないことを示した。

この設計が想定していたのは定型タスクである。履歴が長大になる一方で応答が短い場面なら、履歴を捨てる効果は大きい。今回測ったのはコードを読んで評価する探索的な作業であり、その条件に当てはまらない。
